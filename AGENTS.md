# Repository Guidelines

This contributor guide is regenerated by Clavue `/init` from local repository signals.
For full architecture and cross-cutting concerns, read `clavue.md`. This file is the
quick contributor card.

## Project Structure

- `src/` — runtime source. Layer order: `index.ts` → `agent.ts`/`cli.ts` → `engine.ts` (+ `engine/`) → `providers/` + `tools/` + `skills/` + `hooks.ts` + `mcp/`.
- `src/{graph,guardrails,tracing,sandbox,rag,genui,voice,runtime}/` — v3 capability axes; each is also a subpath import.
- `src/{agent-jobs,issue-workflow,workflow-contract,proof-of-work,orchestration-policy,runtime-profiles,memory,session,retro,improvement,evaluation-loop}.ts` — durable / contract layer (host-neutral, keyed by `runtimeNamespace`).
- `src/subpath/` — barrel files backing `clavue-agent-sdk/{core,tools,contracts,workflow,retro,testing}` exports.
- `tests/` — `node:test` files, run via `tsx`. 60+ test files; pure tests are offline, `*provider*.test.ts` need API keys.
- `examples/` — numbered examples (01–31+); one feature per file. `examples/web/` is the local demo server.
- `docs/` — ships to npm (`package.json#files`). Internal planning under `docs/plans/` and `docs/specs/` also publishes.
- `dist/` — compiled output, **also a release artifact**. Never hand-edit; regenerate with `npm run build`.
- `.clavue/worktrees/` — ephemeral agent worktrees. Do not commit changes inside.

## Build, Test, Development

- `npm run build` — `tsc → dist/`, also runs as `prepack`. The only static check (no lint).
- `npm run dev` — `tsc --watch`.
- `npm run test` — `npx tsx --test tests/*.test.ts` (node:test runner).
- Single file: `npx tsx --test tests/<name>.test.ts`. By name: `--test-name-pattern="..."`.
- Live-API smoke: `npm run test:examples:live`, or `npx tsx examples/<n>-<feature>.ts`.
- Benchmarks: `npm run bench`, `bench:tokens`, `bench:worker`, `bench:engine`. SLOs in `docs/v2_benchmark_report.md`.

## Coding Style & Naming

- TypeScript ESM, `module: NodeNext`, `target: ES2022`, `strict: true`, Node ≥ 18.
- **Relative imports inside `src/` MUST end in `.js`** (not `.ts`). The compiler emits as-is; Node resolves the compiled file.
- No path aliases (`tsconfig-paths` etc.), no Jest / Vitest / mocha / prettier / eslint.
- Public types live in `src/types.ts`; vendor types in `src/providers/types.ts`. Don't re-export vendor SDK types from `src/index.ts`.
- Match surrounding style (2-space indent, named exports, no default exports for public API). Surgical edits — don't reformat code adjacent to your change.

## Testing Guidelines

- One feature → one test file; mirror the source path where possible (e.g. `src/retro/*` ↔ `tests/retro-*.test.ts`).
- Prefer pure offline tests; reach for live-API tests only when the contract requires it.
- After edits, run the smallest relevant test file; before release, run `npm run build && npm run test`.

## Commit & PR Guidelines

- Conventional-style scoped messages: `feat(...)`, `fix(...)`, `docs(...)`, `chore(release): ...`, `test(...)`, `refactor(...)`. Match recent `git log` style.
- PR description: problem, what changed, verification commands run (with output if relevant), any schema-version impact.
- **Schema-version impact is a release-blocker** — bumping any `*_SCHEMA_VERSION` in `src/types.ts` is a breaking change for downstream hosts. Call it out explicitly.

## Adding new public API

1. Implement under the right layer (provider quirk → `src/providers/`, new tool → `src/tools/`, new axis capability → `src/<axis>/`).
2. Export from BOTH `src/index.ts` (root barrel) AND the relevant `src/subpath/*.ts` or axis `index.ts`. Otherwise tree-shaken consumers can't see it.
3. If it's a new tool: register in `src/tools/index.ts`, update `TOOLSETS` and `ToolsetName` (`src/types.ts`).
4. Add or update one numbered file in `examples/`.
5. Update README API reference and `docs/USAGE.md` when behavior changes.

## Security & Agent-Specific

- Never commit credentials, tokens, local auth state, dependency folders, or private runtime directories. `.env.example` is the only env template.
- Treat `clavue.md`, `AGENTS.md`, and compatibility `CLAUDE.md` as a generated baseline owned by `/init`.
- Multi-tenant hosts: isolate `runtimeNamespace`, `session.dir`, and `CLAVUE_AGENT_JOBS_DIR` per tenant.
- Finish work with: changed behavior, the verification command(s) you actually ran, and remaining risks (schema versions, provider quirks, runtime-namespace state).
