# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

> Note: `clavue.md` and `AGENTS.md` are regenerated by Clavue `/init` from repository signals.
> This `CLAUDE.md` is intentionally hand-curated for Claude Code — keep durable architecture
> guidance here, not in those generated files.

## Repository identity

This repo publishes [`clavue-agent-sdk`](https://www.npmjs.com/package/clavue-agent-sdk) — a
production-oriented, in-process TypeScript agent runtime. It is **a library first, a CLI second**.
There is no daemon, no subprocess: `run()` / `query()` / `createAgent()` execute the full agent
loop inside the host process.

The package ships compiled output (`dist/`) and the `docs/` folder (see `package.json#files`), so
`dist/` **is** a release artifact even though it lives in the working tree. Source of truth is
`src/`; never hand-edit `dist/`.

## Common commands

```bash
npm run build                   # tsc → dist/  (also runs as prepack)
npm run dev                     # tsc --watch
npm run test                    # node --test via tsx, runs every tests/*.test.ts

# Run a single test file (preferred during iteration):
npx tsx --test tests/openai-provider.test.ts

# Filter test cases by name within a file:
npx tsx --test --test-name-pattern="retry" tests/retry.test.ts

# Smoke-run every example end-to-end against a live API (needs CLAVUE_AGENT_API_KEY):
npm run test:examples:live

# One specific example file:
npx tsx examples/14-openai-compat.ts

# Local web demo server:
npm run web

# Benchmarks (regression-detection thresholds in docs/v2_benchmark_report.md):
npm run bench                   # all scripts/bench/*.ts
npm run bench:tokens            # token estimator content-class accuracy
npm run bench:worker            # worker_thread spawn / abort latency
npm run bench:engine            # engine footprint (lines, helper count)

# CLI smoke test from built dist:
node dist/cli.js --help
echo "Summarize package.json" | CLAVUE_AGENT_API_KEY=... node dist/cli.js
```

There is **no lint/format script** configured. TypeScript `strict` is on (`tsconfig.json`), and
`tsc` is the only static check — run `npm run build` to typecheck.

### Things that span multiple files (read these together)

- **Provider abstraction.** `src/providers/types.ts` defines `LLMProvider`, `NormalizedMessageParam`,
  `NormalizedTool`, `NormalizedResponseBlock`. `anthropic.ts` and `openai.ts` both implement this
  interface so the engine never branches on vendor. `capabilities.ts` decides per-model features
  (vision, Responses API, parallel tools, prompt caching). When you add a model or fix a vendor
  quirk, do it in the provider — not in `engine.ts`.

- **Tool registry & toolsets.** `src/tools/index.ts` is the single source for `getAllBaseTools()`
  and the named toolsets (`repo-readonly`, `repo-edit`, `research`, `planning`, `tasks`,
  `automation`, `agents`, `mcp`, `skills`). When you add a tool, register it here AND export it
  from `src/index.ts` so consumers can import it. Toolset membership is in `TOOLSETS`
  (src/tools/index.ts) — keep it in sync with `ToolsetName` in `src/types.ts`.

- **Public schema versions.** `src/types.ts` defines the contract version constants:
  `SDK_EVENT_SCHEMA_VERSION`, `AGENT_RUN_RESULT_SCHEMA_VERSION`, `AGENT_RUN_TRACE_SCHEMA_VERSION`,
  `AGENT_JOB_RECORD_SCHEMA_VERSION`, `MEMORY_TRACE_SCHEMA_VERSION`, plus
  `CONTROLLED_EXECUTION_CONTRACT_VERSION` and `PROOF_OF_WORK_SCHEMA_VERSION`. **Bumping these is
  a breaking change for downstream hosts.** Adding optional fields to a record type is fine;
  changing field semantics, removing fields, or renaming enums requires a schema version bump
  and a note in the README.

- **Permission/autonomy/policy.** Three orthogonal axes converge in the engine and `Agent`:
  - `permissionMode` (`PermissionMode` in types.ts) gates *whether* a tool can run.
  - `autonomyMode` (`supervised`/`proactive`/`autonomous`) gates *how often* the agent asks.
  - `qualityGatePolicy` (required gates + fail statuses) gates *whether* a run is "completed".
  Tool policy enforcement lives in `engine.ts` via `canUseTool` + allow/deny + workspace path
  containment in file tools. Don't add ad-hoc safety logic inside individual tools when the
  pattern already exists at the engine layer.

- **Runtime namespacing.** Background AgentJobs, issue workflow runs, cron jobs, and team mailboxes
  are keyed by `runtimeNamespace` (resolved through `src/utils/runtime.ts`). This is what makes
  the SDK safe to embed in multi-tenant hosts. Persisted state goes under `os.tmpdir()` partitioned
  by namespace — never write to a hard-coded location.

- **Workflow modes (`runtime-profiles.ts`).** The 8 named modes (`collect`/`organize`/`plan`/
  `solve`/`build`/`verify`/`review`/`ship`) are pre-baked combinations of toolset, permission
  mode, memory policy, and append-system-prompt. Hosts pass `workflowMode: 'verify'` to get a
  controlled-execution preset. The `ControlledExecutionContract` is part of the public surface;
  changes to the profile shape need a version bump.

- **Retro / eval loop (`src/retro/*`).** This is a deterministic evaluation system that runs
  *outside* the LLM agent loop: evaluators score findings → policy decides accept/retry/abandon →
  ledger persists → optional `runRetroLoop` retries with bounded attempts. It composes with
  `selfImprovement.retro` in `Agent` config. When changing scoring or dimensions, update
  `RETRO_DIMENSIONS` in `src/retro/types.ts` and the evaluators that depend on it.

- **Engine helpers (`src/engine/*.ts`).** `engine.ts` was deliberately split into 15 helper modules
  (compact-stage, dispatch-executor, error-helpers, memory-helpers, message-helpers,
  prompt-helpers, quality-gate-helpers, resilient-call, result-events, single-tool-helpers,
  skill-helpers, tool-helpers, tool-results, turn-bookkeeping, turn-request) to keep `engine.ts`
  under ~1000 lines. When adding logic to the agent loop, prefer extending an existing helper or
  adding a new one over inlining into `engine.ts`. The benchmark `npm run bench:engine` enforces
  the line-count regression threshold.

- **Subpath exports (`src/subpath/*` + v3 axis directories).** The package publishes 13 entry
  points: root + `/core`, `/tools`, `/contracts`, `/workflow`, `/retro`, `/testing`, `/graph`,
  `/guardrails`, `/tracing`, `/sandbox`, `/rag`, `/genui`, `/voice`. The first seven are barrel
  files in `src/subpath/`; the v3 axes export their own `index.ts`. The root `src/index.ts`
  re-exports everything for back-compat. **Adding a new public symbol means updating both** the
  root barrel AND the relevant subpath entry — otherwise tree-shaken consumers won't see it.
  Mappings live in `package.json#exports`; keep them aligned with the actual files.

- **Worker-thread subagent runtime (`src/runtime/worker-thread-*.ts`).** When a subagent is
  configured with `runtime: 'worker_thread'`, it spawns a fresh V8 isolate via
  `worker-thread-subagent.ts` and the `worker-thread-entry.ts` bootstrap. Pre-flight abort
  short-circuits before spawn; env forwarding is curated (no implicit leakage). Latency SLOs are
  enforced by `npm run bench:worker`. Don't add shared registries or globals that assume a single
  process — the isolate has its own.

## TypeScript / module conventions

- **ESM + NodeNext.** All relative imports inside `src/` MUST end in `.js` (not `.ts`) — the
  TypeScript compiler emits as-is and Node resolves the compiled file. New files must follow
  this. Do not introduce `tsconfig-paths` or path aliases.
- `target: ES2022`, `strict: true`, no implicit any. The build is the only typecheck — keep it
  green.
- Tests use `node:test` via `tsx`. Don't add Jest / Vitest / mocha — `npx tsx --test` is the
  contract.
- Public types live in `src/types.ts`. Vendor types live in `src/providers/types.ts`. Don't
  re-export vendor SDK types from `src/index.ts` — keep the surface vendor-neutral.

## Project conventions specific to this repo

- **Generated rule files.** `clavue.md`, `AGENTS.md`, and the auto-generated portion of
  `CLAUDE.md` are owned by Clavue `/init`. Put durable architectural guidance here in
  `CLAUDE.md` (or in `docs/`), not in the generated baseline files.
- **Examples are documentation.** Each numbered file in `examples/` (01–16) demonstrates one
  feature in isolation. When you add a feature, add or update the matching example. The
  `test:examples:live` script runs them all against the live API.
- **`docs/` is published.** It's in `package.json#files`, so docs ship to npm. Keep authoritative
  docs there: `programmatic-integration-guide.md`, `production-agent-sdk-capabilities.md`,
  `agent-sdk-capability-upgrade-program.md`. Internal planning lives under `docs/plans/` and
  `docs/specs/` (also published — be deliberate about what you write there).
- **`.clavue/worktrees/`** holds active agent worktrees from the Clavue runtime. Treat as
  ephemeral; do not commit changes inside.
- **Surgical changes.** When fixing a bug in one provider, don't refactor the other. When adding
  a tool, don't reformat the registry. The `git status` you see at session start often has many
  unrelated dirty worktrees — they are not yours to clean up.

## Environment variables (runtime + tests)

| Variable | Purpose |
|---|---|
| `CLAVUE_AGENT_API_KEY` (or `CLAVUE_AGENT_AUTH_TOKEN`) | LLM API key |
| `CLAVUE_AGENT_API_TYPE` | `anthropic-messages` or `openai-completions` |
| `CLAVUE_AGENT_MODEL` | default model id |
| `CLAVUE_AGENT_BASE_URL` | custom endpoint (proxies, OpenRouter, etc.) |
| `CLAVUE_AGENT_AUTONOMY` | `supervised`/`proactive`/`autonomous` |
| `CLAVUE_AGENT_PERMISSION_MODE` | matches `PermissionMode` union |
| `CLAVUE_AGENT_SELF_IMPROVEMENT` | `1`/`true`/`yes` to opt into run-learning |
| `AGENT_SDK_MAX_TOOL_CONCURRENCY` | cap for parallel read-only tool calls |

The integration tests in `tests/*provider*.test.ts` and `examples/*.ts` need these. Most other
tests (`memory`, `retry`, `tools`, `workflow-contract`, `proof-of-work`, etc.) are pure and run
offline.

## When you finish a task

Summarize: changed behavior, the verification command(s) you actually ran, and any remaining
risks (especially around schema versions, provider quirks, or runtime-namespace state). If you
edited a public type in `src/types.ts` or `src/providers/types.ts`, call that out explicitly —
those are downstream-visible.
